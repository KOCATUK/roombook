## Как сопоставлялись записи

Использовал три признака, и для прогона 22:37 все три сходятся:

1. **Порядок и время.** Запись Postgres идёт через 14–70 мс после записи шлюза с тем же смыслом.
2. **Текст ошибки.** `event_message` из Postgres дословно совпадает со строкой «сообщение:» в `smoke_output.txt`.
3. **`sb-request-id`.** Это наблюдение, а не документированное свойство. Если прочитать первые 48 бит `sb-request-id` как миллисекунды Unix (как в UUIDv7), получится время запроса. Для проверок 3, 4, 10, 11 и 13 оно до миллисекунды совпадает с `timestamp` записи шлюза:

| Проверка | `sb-request-id` | Время из id (UTC) | Время записи шлюза (UTC) |
|---|---|---|---|
| 3 | `01a146dd-3126-…` | 22:37:43.590 | 22:37:43.590 |
| 4 | `01a146dd-31b5-…` | 22:37:43.733 | 22:37:43.733 |
| 6 | `01a146dd-3300-…` | 22:37:44.064 | **записи нет** |
| 8 | `01a146dd-3400-…` | 22:37:44.320 | 22:37:44.307 (−13 мс, причина неизвестна) |
| 10 | `01a146dd-3500-…` | 22:37:44.576 | 22:37:44.576 |
| 11 | `01a146dd-356a-…` | 22:37:44.682 | 22:37:44.682 |
| 13 | `01a146dd-3634-…` | 22:37:44.884 | 22:37:44.884 |

Ни в одной выгрузке нет самого `sb-request-id`: поле `id` у записей лога — это другой идентификатор. Соединять записи приходится по времени.

### Отдельно: статус 23P01

Скрипт и комментарий в `src/api/appError.ts` («PostgREST отдаёт его с 409») ожидают 409 для 23P01. Во всех трёх наблюдениях статус 400: проверка 8, запись шлюза 22:37:44.307 и ручная проверка 22:17:51. Значит, WARN в проверке 8 вызван неверным ожиданием, а не поведением сервера. По моему знанию документации PostgREST, 409 даётся только для 23503 и 23505, а остальные коды класса 23 дают 400. Но в репозитории этой таблицы нет, поэтому сверьте с документацией. Ожидание в `scripts/api-smoke.mjs` исправлено на 400, комментарий в `appError.ts` тоже (коммит `fix(api)` после этого разбора). `smoke_output.txt` оставлен как есть: это вывод прогона до правки. На работу клиента это не влияет: `getKind` проверяет 23P01 раньше статуса.

## 2. Что видно в API Gateway, а что только в Postgres

- **API Gateway** показывает метод, путь с query-строкой, HTTP-статус, `auth_user` (uuid или `null`) и клиента (`node`). Причины ошибки там нет. Все записи 400 выглядят одинаково (`POST | 400 | …/bookings`), хотя одна — пересечение (23P01), а другая — неверный интервал (23514). Все записи 403 тоже одинаковы, хотя одна — RLS, а другая — GRANT.
- **Postgres** показывает код SQLSTATE и текст ошибки, то есть причину. Метода, пути и пользователя там нет (`method`, `pathname` пустые, `auth_user: null`).
- Поэтому диагноз ставится только по паре записей «шлюз + Postgres», соединённых по времени, и по `sb-request-id` клиента.
- Причину можно увидеть и без логов в заголовке ответа: `Proxy-Status: PostgREST; error=23P01` (`conflict_network_400.png`) и `error=42501` (`rest_post_anon_401.png`).

## 3. Расхождение: 7 ответов 4xx против 6 записей шлюза

В прогоне 22:37 клиент получил 7 ответов 4xx (проверки 3, 4, 6, 8, 10, 11, 13). Записей шлюза уровня `warning` за этот интервал 6: нет `POST /rest/v1/rooms` 403 (проверка 6). При этом в Postgres есть запись 22:37:44.089 `permission denied for table rooms`, а значит запрос прошёл через шлюз до БД, и ответ 403 вернулся клиенту. Пропуск касается только логирования. Причину по имеющимся данным установить нельзя. Гипотезы:

| # | Гипотеза | Как проверить |
|---|---|---|
| H1 | Запись есть, но с другим `level`, и фильтр `Level = warning` её скрыл | В Logs → API Gateway снять фильтр Level, поставить Pathname = `/rest/v1/rooms` и найти запись около 22:37:44.064 UTC (01:37:44 МСК). Если она найдётся, посмотреть её `level`. |
| H2 | Запись потеряна или пришла с задержкой при сборе логов | Повторить запрос сейчас: `POST /rest/v1/rooms` с токеном. Через несколько минут поискать запись шлюза. Повторить 2–3 раза и посмотреть, стабилен ли пропуск. |
| H3 | Ошибка выгрузки | Маловероятно: на `logs_api.png` в UI тоже «10 of 10 rows», то есть выгрузка совпадает с UI. Но это не исключает H1. |
| H4 | Запрос к `rooms` записан под другим путём или типом лога | Поискать в Logs по всем типам записи за 22:37:44.0–22:37:44.1 UTC. ## 4. Что можно логировать на клиенте

Проверка выгрузки на `DETAIL`: в `postgres_logs.json` у записей есть только `id, date, method, pathname, status, timestamp, level, event_message, log_type, log_count, logs, auth_user`. Полей `DETAIL`, `detail`, `hint` нет, `logs` везде пустой массив. Есть ли DETAIL в полной записи Postgres на платформе, по выгрузке сказать нельзя.

В ответе клиенту поля `details` и `hint` есть. На `rest_post_anon_401.png` тело такое: `"details": null`, `"hint": "Grant the required privileges to the current role with: GRANT INSERT ON public.bookings TO anon;"`. Для ответов 23P01 и 23514 содержимое `details` в наших файлах не зафиксировано: `smoke_output.txt` печатает только `message`. Комментарий в `src/lib/logger.ts` предполагает, что в `details` попадают значения строк. Проверить это можно, выведя `Object.keys` и длину `details` для 23P01, не печатая сам текст.

| Поле | Логировать на клиенте? | Почему |
|---|---|---|
| `operation`, `kind` (наш `AppError`) | да | Своя классификация, без данных пользователя. Уже логируется в `supabaseApi.ts`. |
| HTTP `status` | да | Нужен для сопоставления с записью шлюза. |
| `code` (SQLSTATE / PGRST) | да | Главный признак причины (23P01, 23514, 42501, PGRST301…). |
| `sb-request-id` | да, предлагаю добавить | По нему находится время запроса и запись шлюза (раздел «Как сопоставлялись записи»). Сейчас клиент его не сохраняет. Как достать заголовок через supabase-js, я в коде не проверял. |
| `message` | осторожно, лучше нет | В наших примерах в нём только имена таблиц и ограничений, значений нет. Но гарантии нет: для других ошибок Postgres текст может включать данные. `code` даёт то же для диагностики. |
| `details` | нет | По комментарию в `logger.ts` в него попадают значения строк. Наши файлы это не опровергают и не подтверждают (см. выше). |
| `hint` | нет | Пользы для клиента нет, а совет может вредить. Пример из `rest_post_anon_401.png` предлагает `GRANT INSERT ... TO anon`, то есть снять намеренную защиту. |
| Полный URL с query | нет, только путь | В шлюзе видно, что query несёт значения фильтров (`id=eq.09925637-…`). В фильтр может попасть и название брони. |
| `auth_user` / `sub` | нет | Идентификатор пользователя. Шлюз и так пишет его на своей стороне (`auth_user`), а в ответах он есть в заголовке `Sb-Jwt-Sub`. |
| Токен, `apikey`, `Set-Cookie` | никогда | Секреты. |
