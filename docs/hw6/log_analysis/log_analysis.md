# Анализ логов с помощью ИИ (ДЗ6, шаг 7)

Дата анализа: 2026-10-17. Источник: экспорт логов проекта Supabase (Dashboard → Logs → Export, JSON),
файл `supabase_logs_sanitized.json` в этой папке.

## Кто что делал

- Пользователь выгрузил логи из панели Supabase и передал файл ИИ-ассистенту в чате (Claude). Текста запроса
  к файлу приложено не было: ассистент сам предложил формат разбора.
- ИИ-ассистент изучил структуру файла, проверил его на секреты, посчитал статистику и составил выводы.
  Числа получены скриптом `analyze_logs.mjs` (результат в `analyze_output.txt`), его можно запустить повторно:
  `node analyze_logs.mjs supabase_logs_sanitized.json`.
- Сам анализ логов выполнил ИИ-ассистент в чате. Агент в репозитории (Claude Code) только закоммитил файлы
  анализа, а по находке L-01 проверил код и внёс правку (коммит `bcf0929`). Другая его работа с логами
  описана в `docs/hw6/monitoring_incident.md` и `backend_documentation.md`.
- Логи Vercel (функции `/api/health`, `/api/log`) в этот файл не входят: из них есть только скриншот двух
  записей `/api/health` со статусом 200. Разбор инцидента 405 на HEAD вынесен в `monitoring_incident.md`.

## Обезличивание

В исходном файле: идентификатор пользователя в поле `auth_user` (заменён на `<user-id-1>`), IP-адресов, e-mail,
JWT, ключей и паролей нет (проверено поиском по шаблонам). Строки User-Agent оставлены: они нужны для различения
устройств. В исходный файл правок кроме замены `auth_user` не вносилось.

## Находки

### L-01. Выход вернул 403 после выхода с «другого устройства» (гипотеза)

- Факт: в 07:21:21 `POST /auth/v1/logout?scope=global` с «телефона» (эмуляция) вернул 204. В 07:26:50
  аналогичный запрос с «десктопа» того же пользователя вернул 403 (единственный ответ ≥ 400 за период).
- Гипотеза: выход со `scope=global` отзывает все сессии пользователя, поэтому десктопная вкладка к 07:26 уже
  держала недействительную сессию, и повторный выход получил 403. По документации Supabase Auth, `signOut()`
  без аргументов имеет глобальную область. Эта причина не подтверждена: в логах нет тела ответа. Подтвердить
  можно в Dashboard → Authentication → Sessions или повторив шаги.
- Следствие для пользователя: выход на одном устройстве выбивает сессии на всех остальных.
- Рекомендация: вызывать `signOut({ scope: 'local' })`, чтобы выход действовал только на текущем устройстве,
  и не считать 403/«session not found» при выходе ошибкой. Проверить `src/hooks/useAuth.ts`, как реализован выход.

### L-02. Лишние чтения: 36 запросов `bookings` и 23 запроса `rooms` на одно создание и одно удаление

- Факт: форм запроса четыре: список броней (26 раз), расписание комнаты с `profiles(display_name)` (10), список
  комнат (20) и пробный `rooms?select=id&limit=1` (3, это health check, он идёт не с клиента).
- Вывод: клиент перечитывает данные при каждом действии и входе, кэша нет. На текущей нагрузке (3 комнаты,
  единицы броней) это не проблема. Рекомендация без срочности: кэшировать список комнат, он почти не меняется.
- Не проверялось: время выполнения запросов (в экспорте нет полей задержки), поэтому о производительности
  вывода сделать нельзя. Задержку Supabase от нашего health check мы знаем отдельно (поле `supabase_ms` в логах
  Vercel: около 460–610 мс на холодный запрос).

### L-03. Доля preflight-запросов 17 из 92 (18 %)

- Факт: 9 `OPTIONS` на `bookings`, 4 на `rooms`, 3 на `token`, 1 на `logout`. Заголовки CORS Data API задаёт
  платформа, настроить их нельзя (описано в `backend_documentation.md`).
- Вывод: это обычная плата за кросс-доменные запросы с заголовком Authorization. Снижается только сокращением
  числа запросов (см. L-02).

### L-04. Postgres без проблем

- Единственные записи: контрольные точки. Медленных запросов, отказов подключения и ошибок за период нет.
  Но запросы, отклонённые триггерами (S-02) и RLS, в этот период не выполнялись, поэтому проверка миграции
  в этих логах не отражена (она подтверждена отдельно, `docs/hw6/harden_check_result.md`).

## Промпт для повторного анализа (шаблон)

Реальный диалог был без текста запроса (см. выше). Чтобы повторить разбор, подойдёт такой промпт:

> Вот экспорт логов Supabase (JSON). Не печатай секреты и идентификаторы пользователей. 1) Опиши структуру
> и проверь файл на токены, ключи, e-mail и IP. 2) Посчитай записи по log_type, level, статусу, методу и пути.
> 3) Выдели все ответы ≥ 400 и сопоставь их с предыдущими событиями той же сессии. 4) Найди повторяющиеся
> запросы и оцени, нужны ли они. 5) Для каждой находки укажи факт из логов, гипотезу и способ проверки.
> Не делай выводов о производительности без полей задержки.
